## 1. Basket from sentiment-scanner doesn't persist (Jason's #1)

**Root cause:** `run_focus_workflow` and `run_unified_flow` call `prompt_index_choice()`
and `_resolve_basket()` unconditionally — even when a `pack_ctx` (sentiment-scanner pack)
was loaded. `_resolve_basket` rebuilds a fresh index-weighted top-N basket via
`index_membership.get_index_constituents`, discarding the pack's tickers entirely except
for the single `focus_ticker`, which gets folded into the new index basket.

The pack's 9 tickers *are* used, but only for the separate Group Screener step — never
for correlation/dispersion. That's why you got "a bigger pull with less insight": the
correlation engine ran against an index-derived basket instead of your 9 names.

**Confirmed locations:**
- `volatility_suite.py` L432 (`run_unified_flow`) and ~L571 (`run_focus_workflow`) —
  unconditional `prompt_index_choice(ticker)` call.
- `volatility_suite.py` L456 / L650 — `_resolve_basket(...)` overwrites `tickers` with an
  index-constituent list regardless of `pack_ctx`.
- `volatility_suite.py` L626-637 — the pack's `group_tickers` (correctly built) only feed
  the group screener call, never `correlation_engine.run_correlation_engine`.
- `correlation_engine.py` L215 (`compute_basket_stats`) / L491 (`run_correlation_engine`)
  — already accepts an arbitrary ticker list with no index dependency (`market_ticker` is
  just a beta benchmark). The capability you want already exists; it's just never called
  with the pack's tickers.
- `suite_context.py` L179-191 — `build_suite_context`/`validate_suite_context` hard-require
  a non-empty `basket.index_ticker`, so the schema itself assumes every basket maps to a
  named index. This needs relaxing, not just the call site.

**Fix:**
1. In both workflow functions, branch on `pack_ctx`: if present, skip `prompt_index_choice`
   and `_resolve_basket` entirely; set `tickers = group_tickers`, `weights = None` or equal
   weights.
2. Feed that basket straight into `ce.run_correlation_engine` so correlation/dispersion
   runs against the actual 9 names.
3. Update `suite_context.py` to accept a `"CUSTOM"` / null sentinel for `index_ticker` when
   the basket came from a pack, instead of requiring a real index name.
4. Keep `prompt_index_choice`/`_resolve_basket` for the manual-ticker path only — that's
   still a valid use case, just not when a pack is loaded.

**Effort:** small — this is a routing fix (skip two calls, change what feeds a third),
not new logic. The hard part (basket-native correlation) already exists.

**Implemented as:** both workflows now branch on `use_pack_basket` (pack loaded AND
>=2 tickers). When true, `prompt_index_choice`/`_resolve_basket` are skipped entirely,
`tickers = group_tickers` (equal-weighted), and `chosen_index` becomes a benchmark-only
value (default `SPY`, overridable via the `VS_BENCHMARK_INDEX` env var) used solely for
the two-leg vol-spread/beta comparison — it no longer determines basket composition.
Section titles reflect which basket was used ("sentiment basket (group-id)" vs.
"{index} constituents"). No `suite_context.py` schema change was needed — `index_ticker`
just needs to be a non-empty string, which the benchmark value already satisfies.

## 2. Screener behaves differently depending on how the universe was built (Jason's #2)

**Root cause:** there are genuinely two screener call sites in `volatility_suite.py`, and
nothing in the output tells you which one you're looking at:

- **Group screener** — L636-637, calls `variance_swap_screener.run_variance_screener(group_tickers, ...)`.
  This is the multi-ticker, comparative one (`variance_swap_screener.py` L368:
  `for t in tickers: ... results.append(r)` — loops and appends correctly, no bug here).
- **Single-name rescreen** — L772-780, printed as `"[Running] Variance Screener
  (single-name score)"`, calls `vss.screen_ticker(focus_ticker, ...)` for one ticker only
  and renders `print_screener_table([r])` — a one-row table by design.

Both run in the same session. The second one isn't broken — it's a different, narrower
step (a recheck on just the focus ticker) that runs later and produces a table that looks
like "the screener" but only has one row. That's exactly what reads as "constantly only
populates one ticker and doesn't compare."

**Fix:**
1. Rename the second step's output header from `"Variance Screener (single-name score)"`
   to something that can't be confused with the group screener, e.g. `"Focus-Ticker
   Recheck (post-basket)"`.
2. In the PDF/report builder, label the two sections distinctly (`"Group Screener: ..."`
   vs `"Focus Ticker Recheck: ..."`) rather than both rendering as generic "Screener Score."
3. Optional: when a group screener already ran in the same session and the focus ticker is
   already in `group_tickers`, skip the redundant single-name recheck and just reference
   the group screener's row for that ticker.

**Effort:** small — labeling/dedup, not a scoring or loop bug.

**Implemented as:** the recheck step is now titled "Focus-Ticker Screener Recheck
(post-basket)" everywhere (console + PDF section), and is skipped entirely (with a short
one-line note pointing back at the Group Screener table) whenever the group screener ran
this session and the focus ticker is already in `group_tickers`.

## 3. Score scale reads as inverted, and missing data silently becomes a real signal

**Root cause, part A (design, not a bug):** the composite score is a *short-vol
attractiveness* score — higher score = vol looks rich = sell it (`variance_swap_screener.py`
L231: `# Composite score (0-100, higher = better for short vol)`). Score ≥80 → STRONG SELL,
score <20 → STRONG BUY (L240-249). This is internally consistent but has no legend in the
PDF, so at a glance a low score next to "STRONG BUY" reads as inverted.

**Root cause, part B (confirmed bug, already flagged in README.md Phase 11 as top
priority, unfixed as of 2026-07-24):** when price history is too short (`len(prices) < 5`,
L219), realized vol is set to `NaN`, but then:

```python
vrp_pct = fair_vol_pct - (rv_match * 100) if not math.isnan(rv_match) else 0.0   # L227
...
rv_30_pct = rv_30 * 100 if not math.isnan(rv_30) else 0.0                          # L255
```

VRP collapses to a flat `0.0` instead of being excluded, and RV_30/60/90 render as `0.0`
in the output table instead of "N/A." This is exactly what happened with SPCX: RV showed
as 0.0 across the board, VRP showed +0.0pp, and — combined with a weak convexity/skew/tail
read from a thin chain — the composite score landed under 20, producing STRONG BUY with no
indication the underlying data was missing rather than genuinely neutral.

README.md's Phase 11 section anticipated this class of bug producing a false STRONG SELL;
the current code's guard produces a false STRONG BUY instead — same underlying defect
(missing input imputed as zero rather than excluded), different failure direction. The
README also separately flags a blanket `except Exception: return None` (L262-263) that
drops failed tickers from the ranking with no indication of why they're missing.

**Fix:**
1. `vrp_pct`, `rv_30/60/90_pct` should be `None`/NaN, not `0.0`, when the source data is
   insufficient — never a value that can pass silently through downstream math.
2. Add a `data_quality` field to `ScreenResult`; when RV couldn't be computed, force
   `signal = "INSUFFICIENT DATA"` regardless of score, and exclude the ticker from the
   ranked bar chart (or visually separate it).
3. Replace the blanket `except Exception: return None` with a typed result carrying the
   failure reason, so a screened list of 9 that returns 6 tells you which 3 failed and why.
4. Add a legend/caption to the screener table and PDF section explaining the score
   direction (low = cheap vol = buy, high = rich vol = sell).
5. Add tests for `screen_ticker`'s scoring function against synthetic chains, including a
   synthetic "insufficient history" case — README already asks for this and notes the
   function is pure and trivially testable.

**Effort:** medium — touches the `ScreenResult` schema, the scoring function, and both
the table renderer and PDF builder.

**Implemented as:** `ScreenResult` gained a `data_quality` field (`"ok"` /
`"insufficient_price_history"`, default `"ok"` for backward compatibility). When a
ticker's price history is too short, `vrp_pct`/`rv_30_pct`/`rv_60_pct`/`rv_90_pct`/
`rv_match_pct` are now `NaN` (never `0.0`), and `signal` is force-set to
`"INSUFFICIENT DATA"` regardless of the numeric score — the score itself is still
computed (using the old 0.0 VRP stand-in internally, so table/chart ordering doesn't
change shape) but can no longer produce a confident BUY/SELL label. `run_variance_screener`
and the standalone CLI now exclude anything not `data_quality == "ok"` from the "Top
short/long candidates" lists and the top-10 ranking chart, and report how many of the
requested tickers were actually screened vs. silently skipped. `print_screener_table`'s
BUY/SELL marker is now derived from `signal` itself instead of independently
re-deriving the same score thresholds (that duplication was its own latent
inconsistency). Covered by a new `tests/test_variance_swap_screener.py` (4 tests,
network-free via mocked ThetaData/price-history calls) — the module had no prior tests.

## 4. Stale/illiquid OI can dominate dealer gamma (no magnitude filtering) — ON HOLD

Jason wants a dedicated thinking session on this before any code changes — the
discussion below is unchanged from the original plan and is a starting point for that
conversation, not something to implement yet.

**Root cause:** `dealer_positioning.py`'s core aggregation only filters `oi > 0`
(L448, L470) — there's no volume-confirms-OI check, no days-since-last-trade check, no
minimum-OI threshold, and no outlier/magnitude cap before OI feeds `gamma_by_strike`,
`dollar_gamma_by_strike`, `vanna_by_strike`, etc. (L487-500). That's why a single deep-OTM
strike with 11,256 contracts of OI — versus everything else in the chain sitting in the
low hundreds — can single-handedly set the sign and magnitude of the whole gamma/vanna
read for a name.

Two existing OI thresholds exist but don't cover this: `MIN_HEDGE_OI = 50`
(`replication_reference.py` L57) only filters which strikes are eligible as
*hedge-candidate* strikes for the replication sign-model, not the core gamma sums.
`MIN_OI_FOR_EDGE = 10` (`options_chain_scanner.py` L67) is scoped to that module's
mispriced-strike detector only and isn't imported by `dealer_positioning.py` at all.

`DEALER_POSITIONING_V2_DESIGN.md` names "stale OI sitting there from a trade three months
ago" (L16) as the core weakness of v1 — but v2 (the shipped `vol_surface_replication`
model) only re-derives the *sign* per strike; it never down-weights or discards abnormally
large or stale OI magnitude. So even with v2 active today, an outsized single-strike OI
print still dominates the dollar-gamma total.

**Fix:**
1. Add a shared OI-quality gate applied to all aggregation sums (not just the replication
   hedge-candidate subset): minimum OI, and ideally a same-day-volume-confirms-OI check
   (if `volume` data is available per strike) to distinguish live interest from a stale
   print.
2. Add an outlier cap — e.g., z-score or percentile-based — so one strike can't contribute
   more than some multiple of the chain's typical per-strike OI to the aggregate gamma/
   vanna totals without at least being flagged in the output.
3. Surface the flag in the report: if a single strike accounts for more than, say, 40% of
   total dollar gamma, print a caption noting that concentration rather than presenting the
   aggregate as if it were broad-based.
4. `POTATOHEDGE_API_REFERENCE.md` notes a vendor-computed GEX endpoint
   (`/api/db/dealer_positioning`) that's documented but never wired in or verified against
   a live response — worth evaluating as an independent cross-check once the above filters
   are in, not before (garbage-in-garbage-out against a second unverified source doesn't
   help).

**Effort:** medium — new filter logic plus a bit of report-surface work to flag
concentration.

## 5. Mode 2 (Unified Cross-Suite Run) ran no analysis and the PDF prompt was a no-op

**Discovered:** a live run with a pack basket, both child suites declined, and "y" to
"Compile outputs into single PDF?" produced `child_suites_requested=0`,
`new_output_files=0`, and an empty output folder apart from `suite_context.json`.

**Root cause:** `run_unified_flow` and `run_focus_workflow` were two structurally
different functions that happened to share some helper calls. `run_focus_workflow` (mode
1) is the one that actually runs the analysis pipeline -- group screener, basket
correlation, variance-swap replication, opportunities read, GARCH, screener recheck,
dealer positioning, options chain scanner -- and, if asked, compiles those results into a
PDF. `run_unified_flow` (mode 2) only ever wrote a `suite_context.json` and, if you opted
in, launched Options_Suite / VaR_Tools_Simulations as separate processes. It never ran
Vol_Suite's own analysis modules itself, and its "Compile outputs into single PDF?"
prompt stored the flag in `suite_context.json` (`controls.compile_pdf`) but nothing ever
read that flag and built anything -- the README lists "merge all + PDF export" as
Phase 14, not-yet-built. Decline both child suites (a completely reasonable thing to do
if you just want the local report) and mode 2 had nothing left to do.

Two smaller, related gaps: mode 2 never asked for the dealer-positioning sign model
(silently defaulting to v1/oi_heuristic instead of v2) or whether to run the options
chain scanner (silently never running it) -- both prompts existed only in mode 1.

**Fix:** the ~250-line analysis pipeline (group screener through options chain scanner)
was extracted out of `run_focus_workflow` into one shared function,
`_run_core_analysis(...)`. Both `run_focus_workflow` and `run_unified_flow` now call it
with the same arguments (ticker, basket, expiry, sign model, options-chain toggle), so
"running the suite" means the same thing regardless of entry point. `run_unified_flow`
now also asks the sign-model and options-chain-scanner questions (via a shared
`_prompt_sign_model_and_options_chain` helper, so the two modes can't drift apart on this
again), and its PDF prompt now actually calls `compose_pdf_report` on the sections
`_run_core_analysis` returns -- the same call mode 1 makes. The two modes still differ
exactly where they should: mode 1 stops after the analysis + optional PDF; mode 2
additionally writes `suite_context.json` and can launch the sibling suites.

Also renamed the summary field `new_output_files` (which only ever measured files added
by child suites, but read like "how many files did this run produce") to
`child_suite_new_files`, and added `analysis_output_files` for the real total.

**Tested:** `tests/test_run_modes_smoke.py` (new) runs both `run_unified_flow` and
`run_focus_workflow` end-to-end with every network-facing module and stdin scripted and
stubbed, and asserts each pipeline step was actually invoked with the pack's basket (not
an index-derived one), that the sign-model choice reached dealer positioning, that the
options chain scanner ran, and that the redundant single-ticker screener recheck was
correctly skipped -- i.e. it exercises issues 1, 2, and 5 together across both entry
points in one pass. `py_compile` alone would not have caught a wrong keyword argument in
a refactor this size; this test actually calls the functions.
