## 1. `hedge_requirement` understated by a factor of spot price (CRITICAL)

**File:** `dealer_positioning.py:536`

**Root cause:** the headline dealer-hedging statistic — printed and charted everywhere
as "shares per 1% move" (`sh/1%`) — divides by `spot` when it shouldn't.

```python
hedge_requirement = abs(net_dollar_gamma * 0.01) / spot if spot > 0 else 0.0
```

The module's own comment two lines above establishes the relevant identity:

```python
# Gamma "shares/$1" exposure = sign*gamma*OI*CONTRACT_MULTIPLIER, which is
# exactly dollar_gamma_arr / spot (dollar_gamma already carries the
# CONTRACT_MULTIPLIER and a spot factor -- dividing it back out avoids
# summing the same thing twice under a different name).
gamma_shares_arr = dollar_gamma_arr / spot if spot > 0 else np.zeros_like(dollar_gamma_arr)
```

i.e. `dollar_gamma_arr = gamma_shares_arr * spot`, where `gamma_shares_arr` is already
"shares of delta change per $1 move in the underlying." For a 1% move (`ΔS = 0.01·spot`),
the shares dealers must trade is `net_gamma_shares · ΔS = net_gamma_shares · 0.01 · spot`.
Since `net_dollar_gamma = net_gamma_shares · spot`, that simplifies to exactly
`net_dollar_gamma * 0.01` — **no division by spot at all.**

**Worked example (confirmed independently by both review rounds):** gamma=0.05,
spot=$200, OI=1,000 contracts, multiplier=100 → `net_dollar_gamma = 0.05*200*100*1000 =
1,000,000`. A 1% move is $2, so shares needed = `(1,000,000/200)*2 = 10,000`. Current code
computes `1,000,000*0.01/200 = 50` — off by exactly the erroneous `/spot` (a 200x
understatement here; the understatement factor equals the underlying's spot price, so it
gets worse for higher-priced names).

**Downstream effects that fix themselves automatically once this line is corrected — do
not separately patch these:**
- `hedge_notional = result.hedge_requirement * result.spot` (line ~1095) is currently
  printed as a dollar notional but its value today numerically equals what the *correct
  share count* should have been (a second-order symptom of the same bug, not a separate
  one). Once `hedge_requirement` is fixed, `hedge_notional` becomes a genuine dollar
  notional (shares × spot) and needs no code change — just re-verify the printed label
  still reads correctly against a real number.
- `hedge_equiv_option_contracts = hedge_requirement / (abs(hedge_leg.delta) *
  CONTRACT_MULTIPLIER)` (line 557) is computed directly from `hedge_requirement` and
  self-corrects the same way.

**Fix:**
```python
hedge_requirement = abs(net_dollar_gamma * 0.01)
```
(drop the `if spot > 0 ... else 0.0` spot guard too, since the expression no longer
divides by spot — though `net_dollar_gamma` will already be 0 if there were no valid
gamma records, so this is a simplification, not a behavior change on the empty-input
path. Double check `spot` isn't needed for a different guard elsewhere in this block
before deleting the conditional outright.)

**Tests to add:** a synthetic unit test asserting the worked example above
(gamma/spot/OI/multiplier → expected 10,000 shares), since nothing currently checks this
number's magnitude, only that it runs.

**Effort:** small — one-line fix, but re-run every existing dealer-positioning chart/report
comparison once changed, since every prior run's printed hedge number will now read
~`spot`× larger, which will look alarming if nobody expects it.

## 2. `compute_basket_stats` crashes (KeyError) on any basket ticker with failed price history (MAJOR)

**File:** `correlation_engine.py:215-293` (function `compute_basket_stats`)

**Root cause:** the function correctly filters bad tickers out of the *returns frame*:

```python
basket_returns = returns[[t for t in tickers if t in returns.columns]].dropna()
```

but every downstream usage still iterates the **original, unfiltered** `tickers` list
and/or the **original, unfiltered** `weights` array:

- Line 238: `for t in tickers: r = basket_returns[t].values` → `KeyError` the moment any
  ticker's price history failed to fetch (see `fetch_price_history`, which silently drops
  a ticker rather than raising, by design).
- Line 278: `weighted_avg_vol = np.sum([w * individual_vols[t] for w, t in zip(weights,
  tickers)])` — same problem a second time, plus a `weights`/`tickers` length mismatch if
  any tickers were ever actually dropped upstream (weights is never re-filtered either).
- Line 281-282: the returned `BasketStats(tickers=tickers, weights=weights, ...)` reports
  the original requested universe, not what was actually computed — misleading even if
  the crash above is fixed, since the caller has no way to tell a ticker was silently
  dropped.

**Confirmed reachable:** `fetch_price_history` (line 117) drops a ticker's column
entirely (prints `[ThetaData] No usable history for {t}.` or `History fetch failed`) with
no exception raised to the caller — this is deliberate per-ticker graceful degradation,
which is exactly what makes the crash downstream avoidable but currently isn't avoided.
Caught by a bare `except Exception` in `volatility_suite.py:584`, so it doesn't crash the
whole program — but it **silently drops the entire correlation/dispersion section** from
that run's report with only a console print, which directly undercuts the recently-shipped
basket-persistence fix (FIX_PLAN_20260725.md issue 1): a 9-name sentiment pack with one bad
ticker now produces *zero* correlation output instead of correlation on the other 8.

**Fix:** filter once, at the top of the function, into a single source of truth used
everywhere below instead of patching each call site independently:

```python
valid_tickers = [t for t in tickers if t in returns.columns]
dropped = [t for t in tickers if t not in valid_tickers]
if dropped:
    print(f"  [correlation_engine] Dropping {len(dropped)} ticker(s) with no usable "
          f"price history: {dropped}")
if not valid_tickers:
    raise ValueError("No tickers in basket have usable price history.")

# Re-filter weights positionally against the ORIGINAL tickers/weights pairing,
# then renormalize over the survivors.
if weights is None:
    valid_weights = np.ones(len(valid_tickers)) / len(valid_tickers)
else:
    weights_arr = np.array(weights)
    keep_mask = [t in valid_tickers for t in tickers]
    valid_weights = weights_arr[keep_mask]
    valid_weights = valid_weights / np.sum(valid_weights)
```

Then replace every remaining use of `tickers`/`weights` in the function body (the
per-ticker loop, `weighted_avg_vol`, and the `BasketStats(...)` return) with
`valid_tickers`/`valid_weights`. Report `dropped` back to the caller too (e.g. as a new
`BasketStats.dropped_tickers` field) so `volatility_suite.py`'s report can note which
names were excluded and why, matching this project's established convention (README
Phase 11 / FIX_PLAN issue 3: "a failure is reported as an absence... the summary needs to
say how many were excluded and why").

**Tests to add:** a synthetic test calling `compute_basket_stats` with a ticker list where
one entry has no matching column in the returns frame, asserting it returns successfully
on the remaining tickers (not a `KeyError`) and reports the dropped name.

**Effort:** medium — touches the function's control flow in three places plus the
`BasketStats` schema (one new optional field), not a one-line patch.

## 3. Stage 3 backtest annualizes realized vol with calendar days instead of trading days (MAJOR)

**File:** `backtest_stage3.py:69, 178`

**Root cause:**

```python
TRADING_DAYS_PER_YEAR = expiry_selector.DEFAULT_A   # = 365, calendar days
...
return float(np.std(log_rets, ddof=1) * math.sqrt(TRADING_DAYS_PER_YEAR))   # line 178
```

`log_rets` (line 175) are computed from **consecutive trading-day closes**
(`np.diff(np.log(prices))` over `closes_from_today`, a list of trading-day closing
prices). Annualizing trading-day log-return volatility requires `sqrt(252)`, not
`sqrt(365)`. This is the *exact* bug `variance_swap_live.py` already found and fixed
elsewhere in this codebase — its own header comment (lines 25-36) explicitly separates
`DEFAULT_A=365` (calendar days, for expiry-date math only) from `TRADING_DAYS=252`
(trading days, for vol annualization) specifically because conflating them was a
previously-shipped bug. `backtest_stage3.py` imports `expiry_selector` for date math and
then reuses its `DEFAULT_A` for vol annualization too, reintroducing the same conflation
in a different module.

**Consequence:** every `fwd_realized_vol` value Stage 3 computes and reports is inflated
by `sqrt(365/252) ≈ 1.204`, i.e. ~20% too high in absolute terms. Because the scale factor
is common to both the short-gamma and long-gamma day groups, the Welch t-test's
significance/p-value is **not** affected — the backtest's core conclusion (does v2's sign
convention show a bigger, more significant gap than v1's) survives — but every *absolute*
realized-vol number in Stage 3's output (console prints, any chart, any report text citing
"X% forward realized vol") is wrong by a consistent ~20%.

**Fix:**
```python
TRADING_DAYS_PER_YEAR = 252  # trading days/year, for realized-vol annualization from
                              # trading-day closes. NOT expiry_selector.DEFAULT_A (365,
                              # calendar days, used only for expiry-date resolution) --
                              # see variance_swap_live.py:25-36 for why these must stay
                              # separate; conflating them was already a bug fixed there once.
```
(Simplest fix: hardcode `252` locally with the comment above, matching how
`variance_swap_live.py` and `variance_swap_screener.py` each define their own local
`TRADING_DAYS = 252`. Do not import `expiry_selector.DEFAULT_A` for this constant.)

**Tests to add:** `tests/test_backtest_stage3.py` should get a synthetic-price test for
`_forward_realized_vol` with a known input series and hand-computed expected output using
`sqrt(252)`, so a future regression back to `sqrt(365)` fails a test instead of requiring
someone to notice a ~20% drift by eye.

**Effort:** small — one constant, but re-run the backtest once fixed and expect every
reported vol number to drop ~17% (1/1.204), which is expected, not a new problem.

## 4. Missing ATM implied vol silently becomes `0.0`, fabricating convexity premium (MAJOR)

**Files:** `variance_swap_live.py:164-167`, `variance_swap_screener.py:159-162`
(identical pattern in both)

**Root cause:**
```python
atm_iv = chain.call_iv[idx] if atm_strike >= F else chain.put_iv[idx]
if math.isnan(atm_iv):
    atm_iv = chain.put_iv[idx] if atm_strike >= F else chain.call_iv[idx]
if math.isnan(atm_iv):
    atm_iv = 0.0          # <-- fabricates a real-looking value from missing data
...
convexity_premium = fair_vol - atm_iv
```

When neither the call nor the put IV at the ATM strike is available (thin/no liquidity —
plausible on real ThetaData responses), `atm_iv` becomes `0.0` instead of staying
missing. `convexity_premium` then comes out equal to the **entire** `fair_vol` instead of
the normal small (few-percentage-point) spread.

In `variance_swap_screener.py`, this fabricated `convexity_pct` feeds directly into the
composite score:
```python
score += 20.0 * min(max((5.0 - convexity_pct) / 5.0, 0.0), 1.0)  # Low convexity = good
```
Since a fabricated `convexity_pct ≈ fair_vol_pct` is almost always well above 5, this term
clamps to `0.0`, silently docking the ticker's full 20-point convexity weight — the same
"missing input imputed as a real, scoreable value instead of being excluded" defect class
that FIX_PLAN_20260725.md issue 3 already fixed for realized vol, recurring here in a spot
that fix pass didn't touch. `variance_swap_live.py`'s single-ticker script isn't ranked
against anything, so there the consequence is a misleading printed/plotted number rather
than a corrupted ranking — still worth fixing for consistency, but lower stakes.

**Fix — mirror the existing `insufficient_data` pattern from FIX_PLAN issue 3 exactly,**
rather than inventing a new convention:

1. In both `compute_fair_variance_strike` functions, when both call and put ATM IV are
   NaN, leave `atm_iv` as `float('nan')` (do not fall back to `0.0`). `convexity_premium`
   will then naturally come out `NaN` too — no separate change needed for that line.
2. In `variance_swap_screener.py`'s `screen_ticker`, check `math.isnan(atm_iv_pct)` (or
   equivalently `math.isnan(convexity_pct)`) the same way `insufficient_data` is already
   checked for realized vol (see lines 234-247): add an `insufficient_atm_iv` condition,
   OR-it into `insufficient_data` (or a renamed umbrella flag) so `signal` is force-set to
   `"INSUFFICIENT DATA"` in this case too, and use a `convexity_for_score` stand-in
   (`0.0`, same pattern as `vrp_for_score`) so score/ranking-chart shape doesn't change
   unexpectedly for tickers that hit this path.
3. In `variance_swap_live.py`, the single-ticker script's print/plot code needs to render
   "N/A" for `atm_iv`/`convexity_premium` instead of `0.0` when NaN (check the CLI print
   statements and any matplotlib annotation that currently assumes a numeric value).

**Tests to add:** extend `tests/test_variance_swap_screener.py` with a synthetic chain
where both call and put IV are NaN at the ATM strike, asserting `signal ==
"INSUFFICIENT DATA"` and `convexity_pct` is NaN in the output (mirroring the existing
insufficient-price-history test already in that file).

**Effort:** medium — touches `compute_fair_variance_strike` in two files, `screen_ticker`,
`ScreenResult`'s data-quality logic, and `variance_swap_live.py`'s display code.

## 5. Screener's fair-variance formula omits the DDKZ boundary correction (MINOR)

**Files:** `variance_swap_screener.py:142-154` vs. `variance_swap_live.py:140-158`

**Root cause:** `variance_swap_live.py` includes the Demeterfi-Derman-Kamal-Zou
discretization correction for the strike closest to (but at/below) the forward:

```python
replication_term = (2.0 * math.exp(chain.r * T_years) / T_years) * weighted_sum
below = K[K <= F]
K0 = float(below.max()) if below.size else float(K.min())
boundary_correction = (1.0 / T_years) * ((F / K0 - 1.0) ** 2) if K0 > 0 else 0.0
fair_variance = replication_term - boundary_correction
```

`variance_swap_screener.py`'s copy of the same function has no such term:

```python
fair_variance = (2.0 * math.exp(chain.r * T_years) / T_years) * weighted_sum
```

Grepped for any comment/docstring explaining an intentional divergence between the two
copies — none found. `variance_swap_live.py`'s own comment says omitting this term
"slightly overstated the fair variance," so the screener still carries that same small
overstatement, which biases `convexity_premium` and `VRP` slightly toward SELL relative to
what the live module would compute for the identical chain.

**Fix:** port the `boundary_correction` block verbatim into
`variance_swap_screener.py`'s `compute_fair_variance_strike`. Longer-term (optional,
larger effort, not required for correctness): these two functions are now identical
except for this drift — worth collapsing into one shared implementation (e.g. in a shared
module, or have the screener import `variance_swap_live.compute_fair_variance_strike`
directly) so the two can't silently diverge again. Flagging as a follow-up, not blocking
this fix.

**Tests to add:** a synthetic-chain test asserting both modules' `compute_fair_variance_strike`
produce the same `fair_variance_annualized` for an identical input chain.

**Effort:** small.

## 6. `bs_gamma`/`bs_gamma_vec` omit the dividend discount factor (MINOR)

**File:** `dealer_positioning.py:190-208`

**Root cause:** Black-Scholes gamma with a continuous dividend yield `q` is
`Γ = e^{-qT} · N'(d1) / (S·σ·√T)`. The code computes `d1` correctly (with the `(r-q)`
drift term) but never applies the `e^{-qT}` discount factor to the result:

```python
def bs_gamma(S, K, T, r, q, sigma):
    ...
    d1 = (math.log(S / K) + (r - q + 0.5 * sigma * sigma) * T) / sigma_sqrt_T
    return norm_pdf(d1) / (S * sigma_sqrt_T)   # missing exp(-q*T)
```
Same omission in the vectorized `bs_gamma_vec` (line 206). By contrast,
`replication_reference.py`'s `_bs_vega` correctly includes `S * math.exp(-q * T) *
norm_pdf(d1) * sqrtT` — so this codebase already knows the correct pattern elsewhere, it
just wasn't applied here.

**Consequence:** gamma is systematically overstated by a factor of `e^{qT}` whenever
`q > 0`. `bs_gamma_vec` feeds the live hedging-heatmap surface (`dealer_positioning.py`
around line 590, using each ticker's real fetched dividend yield), and `bs_gamma` is
called directly by `backtest_stage3.py:242` for every price-derived (non-vendor-greeks)
gamma record. For SPY (`q≈1.2%`, mostly short-dated `T`) the effect is small (~0.1-0.3%);
it grows for a higher-yield or longer-dated underlying run through the same code paths
(e.g. `q=5%`, `T=1yr` → ~5% overstatement).

**Fix:**
```python
def bs_gamma(S, K, T, r, q, sigma):
    ...
    return math.exp(-q * T) * norm_pdf(d1) / (S * sigma_sqrt_T)
```
and the equivalent one-line change in `bs_gamma_vec`.

**Tests to add:** a unit test comparing `bs_gamma` against a known reference value for
`q > 0` (e.g. from a textbook or a trusted third-party BS calculator) — current tests
likely only exercise `q=0` cases if they exercise this function at all; check
`tests/test_dealer_positioning_sign_model.py` for coverage gaps here.

**Effort:** small.

## 7. Stage 3 backtest's forward price omits the dividend yield it defines (MINOR)

**File:** `backtest_stage3.py:309`

**Root cause:** every other forward-price function in this codebase
(`dealer_positioning.compute_forward_price`, and the identically-named functions in
`variance_swap_live.py`/`variance_swap_screener.py`) computes `S0 * exp((r-q)*T)`.
`backtest_stage3.py` defines its own flat dividend yield with a comment stating plainly
that it "matters only through the forward and through the IV inversion" (lines 84-88:
`_BACKTEST_Q = 0.012`), but the actual forward computation never applies it:

```python
forward = spot * math.exp(_BACKTEST_R * T)   # _BACKTEST_Q never applied here
```

`_BACKTEST_Q` **is** correctly threaded into the IV inversion (line 233) and the
price-derived gamma calc (line 242) — only the forward is missing it.

**Consequence:** `forward` feeds `_net_gamma_v2` →
`vol_surface_reference.compute_vol_surface_reference(..., forward=forward, ...)`, which
uses it as the OTM put/call boundary, the SABR ATM-pin index, and the SABR `F` parameter.
A forward biased high by the missing `e^{-qT}` discount shifts all three — on the order of
tens of basis points for SPY at `q=1.2%`, larger for a higher-dividend name.

**Fix:**
```python
forward = spot * math.exp((_BACKTEST_R - _BACKTEST_Q) * T)
```

**Tests to add:** assert `forward < spot * exp(_BACKTEST_R * T)` for `_BACKTEST_Q > 0` in
a synthetic test, or directly check the computed value against a hand-calculated one.

**Effort:** small.

## 8. Possible day-over-day OI misattribution in replication accumulation (UNCONFIRMED — investigate before fixing)

**File:** `replication_reference.py:606` (`_accumulate_from_history`)

**Root cause (plausible, not confirmed):**
```python
oi_today = oi_by_date[d].get((k, right), 0)
oi_prev  = oi_by_date.get(prev_d, {}).get((k, right), 0)
delta_oi = oi_today - oi_prev
```
If a strike is simply absent from the previous day's OI snapshot (a vendor gap) rather
than genuinely having zero open interest that day, `oi_prev` defaults to `0`, making
`delta_oi` equal the strike's *entire* outstanding OI rather than the true day-over-day
change — misattributing existing position as "new flow acquired that day."

**Why this is flagged as unconfirmed rather than a fix item:** this depends entirely on
whether ThetaData's bulk historical OI endpoint reliably returns every listed strike every
day (in which case absence really does mean 0, and there's no bug) or only strikes with
nonzero OI (in which case absence is genuinely ambiguous). The module's own docstring
describes this endpoint as new and not yet live-smoke-tested.

**Before touching this:** run the module against a real multi-day ThetaData pull and check
whether strikes disappear and reappear across days in a pattern consistent with "endpoint
only returns nonzero-OI strikes" (if so, this is real) or "endpoint returns the full chain
every day, OI just happened to hit zero" (if so, no bug exists).

**If confirmed, fix direction:** distinguish "strike absent from that day's snapshot" from
"strike present with OI=0" — e.g. only compute `delta_oi` for strikes present in both
`oi_by_date[d]` and `oi_by_date[prev_d]`, and print a per-day count of "strikes seen today
but missing yesterday" the way `_build_day_records` already does for the gamma/OI/close
date-coverage intersection (same instrumentation pattern, different join).

**Effort:** investigation first (small); fix effort depends on what's found (likely
small-to-medium).
