CUDA / CuPy canary probe failure — cause and fix
=================================================

Symptom: importing `cupy` and doing any GPU op (e.g. `cupy.array([1.0]) + 1`)
raises `ChildProcessError: Canary probe child process exited with code 1`,
with the child process's own traceback ending in:

    File ".../typing.py", line 1359, in <module>
        class Callable(extra=collections_abc.Callable, metaclass=CallableMeta):
    File ".../typing.py", line 1007, in __new__
        self._abc_registry = extra._abc_registry
    AttributeError: type object 'Callable' has no attribute '_abc_registry'

Cause: a stray, ancient `typing.py` sitting directly in the venv's
`site-packages` (a leftover from a very old package that vendored a
Python-2-era backport of the `typing` module) shadows the standard-library
`typing` module for any subprocess launched with that site-packages on
`sys.path`. `cuda.pathfinder` spawns a child process to run its
CTK-root canary probe (`_resolve_system_loaded_abs_path_in_subprocess`);
that child does `from typing import TYPE_CHECKING` inside
`cuda.pathfinder._dynamic_libs.load_dl_common`, imports the shadowing
`typing.py` instead of the stdlib one, and crashes on a Python 2/3
compatibility shim (`_abc_registry`) that doesn't exist on modern Python.
This breaks header/library discovery for CuPy's CUDA toolkit detection,
not CUDA itself.

Fix: remove (or rename) the stray `typing.py` from the venv's
`site-packages` so the stdlib `typing` module resolves normally, then
reinstall/upgrade whatever package placed it there if it's still needed.
